# Refactor: PaymentGateway — tách cổng thanh toán độc lập

> Bản ghi nguyên văn buổi refactor: tách interface `PaymentGateway` để `PaymentService` không phụ thuộc cổng cụ thể (Strategy pattern + DIP), xử lý "leaky abstraction", so sánh tích hợp MoMo/PayPal, và toàn bộ Q&A của người học. Ngữ cảnh: sau khi code + test E2E Payment VNPay xong, người học chủ động tách sẵn 1 interface để mở rộng cổng khác, nhờ review.

---

## Người học hỏi: Tôi tách 1 interface để sau triển khai cổng khác, hợp lý không? MoMo/PayPal tích hợp có tương tự không?

Trạng thái người học tự làm:
- Tạo `IPaymentGateway` (`createPaymentUrl`, `verifySignature`).
- `VnpayService implements IPaymentGateway` + `@ConditionalOnProperty(name="payment-gate.type", havingValue="vnpay", matchIfMissing=true)`.
- `PaymentService` inject `IPaymentGateway` thay vì `VnpayService`.
- Đổi config prefix `payment-gate.vnpay`, thêm `payment-gate.type`.
- `hmacSha512` chuyển thành `private`.

# Review: `IPaymentGateway`

## ✅ Làm tốt (đúng nguyên lý senior)

1. **Dependency Inversion Principle (DIP).** `PaymentService` phụ thuộc **interface**, không phải class cụ thể `VnpayService`. Chữ D trong SOLID — module cấp cao (business) không phụ thuộc chi tiết cấp thấp (VNPay), cả hai phụ thuộc abstraction.

2. **`@ConditionalOnProperty` chọn impl theo config** — đổi `payment-gate.type` là swap cổng không sửa code. `matchIfMissing=true` giữ VNPay mặc định.

3. **`hmacSha512` thành `private`** — đúng, chi tiết nội bộ, không thuộc contract interface.

4. **Config gom namespace `payment-gate.vnpay.*`** — sạch, mở đường cho `payment-gate.momo.*`.

## 🔴 Vấn đề lớn: abstraction bị RÒ RỈ (leaky) ở tầng callback

Interface mới chỉ trừu tượng hóa **nửa đi** (tạo URL + verify chữ ký). Nhưng **nửa về (xử lý IPN) vẫn dính chặt VNPay** trong `PaymentService.handleIpn`:
```java
params.get("vnp_TxnRef")          // ← key riêng của VNPay
params.get("vnp_Amount")          // ← key riêng của VNPay
params.get("vnp_ResponseCode")    // ← key riêng của VNPay
return new VnpayIpnResponse(...)  // ← format response riêng của VNPay ("00"/"01"/"97")
```
Mục tiêu là làm `PaymentService` không biết gì về VNPay, nhưng `handleIpn` vẫn hardcode toàn VNPay. Cắm MoMo vào, IPN của MoMo có key hoàn toàn khác (`orderId`, `resultCode`, `transId`...) và format response khác → `handleIpn` **không tái sử dụng được**.

Interface mới trừu tượng đúng phần **dễ** (build URL) nhưng bỏ sót phần **khó** (diễn giải callback + quyết định thành/bại + format biên nhận).

**Hình đúng của abstraction** — interface phải gánh cả việc "dịch callback riêng của cổng → kết quả trung lập":
```java
public interface PaymentGateway {
    String getProvider();                                   // "vnpay" | "momo" — chọn runtime (nếu multi)
    String createPaymentUrl(Long orderId, String txnRef, BigDecimal amount, String ipAddr);
    boolean verifySignature(Map<String,String> params);
    PaymentCallback parseCallback(Map<String,String> params);   // ← THÊM: dịch về DTO trung lập
}
public record PaymentCallback(String txnRef, long amount, boolean success, String providerTxnNo) {}
```

Khi đó `handleIpn` mới thật sự **gateway-agnostic**:
```java
if (!gateway.verifySignature(params)) return ackInvalid();
PaymentCallback cb = gateway.parseCallback(params);   // VNPay/MoMo tự dịch key của mình
Payment payment = paymentRepository.findByTxnRef(cb.txnRef())...   // logic domain KHÔNG biết cổng nào
if (payment.getStatus() != PENDING) return ackAlreadyDone();
if (cb.amount() != expected) return ackInvalidAmount();
if (cb.success()) { payment.SUCCESS; order.CONFIRMED; } else { payment.FAILED; }
```

Logic **nghiệp vụ** (tra txnRef, idempotency, khớp tiền, đổi status) là **chung mọi cổng** → ở `PaymentService`. Việc **dịch key + ký + format ack** là **riêng từng cổng** → trong impl. Đó mới là ranh giới đúng.

> Lưu ý thực tế: format ack response (VNPay đòi `{RspCode,Message}`, MoMo đòi HTTP 204, PayPal đòi 200 rỗng) + kiểu request (VNPay GET query, MoMo POST JSON) khác nhau tới mức **controller endpoint vẫn phải riêng từng cổng**. Không thể unify 100% ở controller — và điều đó là bình thường.

## 🟡 Câu hỏi thiết kế: 1 cổng hay NHIỀU cổng cùng lúc?

`@ConditionalOnProperty` nghĩa là **cả app chỉ dùng ĐÚNG 1 cổng** (chọn lúc khởi động). Nhưng e-commerce thật thường cho user **chọn cổng lúc checkout** → cần **nhiều impl sống song song**, chọn theo từng giao dịch:
```java
// Spring tự inject TẤT CẢ bean PaymentGateway vào Map, key = getProvider()
private final Map<String, PaymentGateway> gateways;   // {"vnpay": ..., "momo": ...}
PaymentGateway gw = gateways.get(request.getProvider());  // chọn theo user
```
→ Hỗ trợ nhiều cổng đồng thời → **bỏ `@ConditionalOnProperty`**, để tất cả impl là bean, chọn runtime bằng Map/factory. `@ConditionalOnProperty` chỉ hợp khi **cả đời app chỉ 1 cổng**. (Dự án này giữ 1 cổng cho gọn — ghi backlog nếu cần multi.)

## 🟢 Nhỏ: tên `IPaymentGateway`
Tiền tố `I` là convention **C#/.NET**, không phải Java. Java idiomatic là `PaymentGateway` trần (impl thêm hậu tố: `VnpayGateway`, `MomoGateway`).

## MoMo / PayPal — cách tích hợp có tương tự không?

**Về TƯ DUY: giống hệt.** Cả 4 cổng (VNPay, MoMo, PayPal, Stripe) đều cùng khung xương:
```
tạo giao dịch → redirect user → user trả tiền → callback (webhook/IPN) là source of truth
              → verify chữ ký → idempotency → cập nhật đơn
```
**Về CƠ CHẾ: khác nhau ở chi tiết** — lý do interface (`parseCallback`, `verifySignature`) có giá trị: mỗi impl giấu phần khác biệt của mình.

| | **VNPay** | **MoMo** | **PayPal** |
|---|---|---|---|
| **Tạo giao dịch** | Tự build URL (client-side) | **Server-to-server**: POST API MoMo → nhận `payUrl` | OAuth2 lấy token → REST Orders API → approval link |
| **Chữ ký** | HMAC-**SHA512**, sort **alphabet** | HMAC-**SHA256**, thứ tự field **cố định** | **Cert-based bất đối xứng** (không phải shared secret!) |
| **Callback** | GET query `vnp_*` | POST **JSON** `resultCode`... | POST **webhook event** JSON |
| **Verify callback** | tự ký lại + so | tự ký lại + so | gọi **API PayPal verify** hoặc check cert |
| **Ack response** | `{"RspCode","Message"}` | HTTP **204** | HTTP **200** rỗng |
| **SDK Java** | Không (tự làm) | Không (tự làm) | **Có** SDK chính thức |

**Ba điểm khác đáng chú ý:**

1. **MoMo/PayPal tạo giao dịch bằng server-to-server API call**, không chỉ build URL như VNPay. `createPaymentUrl` của `MomoGateway` bên trong sẽ **gọi HTTP POST tới MoMo** (dùng `RestClient`/`WebClient`) rồi lấy `payUrl`. Interface `String createPaymentUrl(...)` vẫn đúng, chỉ impl phức tạp hơn.

2. **PayPal verify webhook bằng bất đối xứng (cert), không phải HMAC shared secret.** PayPal ký bằng **private key của nó**, mình verify bằng **public cert** tải từ PayPal. Mình *không* giữ secret của PayPal → **không giả lập webhook PayPal được** như cách tự ký IPN VNPay giả. Hệ quả trực tiếp của asymmetric.

3. **MoMo chốt thứ tự field cố định khi ký**, không sort alphabet như VNPay. Bê nguyên `TreeMap.sort` của VNPay sang MoMo → **sai chữ ký**. Mỗi cổng có "luật ký" riêng.

**Tóm lại:** interface là **nền đúng** để cắm MoMo/PayPal — chỉ cần (a) đẩy nốt phần diễn giải callback (`parseCallback` + DTO trung lập) vào interface để `handleIpn` hết dính VNPay, và (b) quyết định 1-cổng vs nhiều-cổng.

**Người học chọn:** ưu tiên test E2E trước, ghi refactor vào backlog. → E2E 6/6 pass với bản committed (chưa interface). Sau đó quay lại hoàn thiện refactor.

# Hoàn thiện refactor

## Thiết kế đích
```
PaymentGateway (interface)                PaymentService (agnostic)
├─ createPaymentUrl(...)          ┐        handleIpn:
├─ verifySignature(params)        │          verify → parseCallback → tra Payment
├─ parseCallback(params)          │          → idempotency → khớp tiền → cập nhật
│    → PaymentCallback (trung lập) │          → buildIpnResponse(result)
└─ buildIpnResponse(IpnResult)    ┘        (KHÔNG còn vnp_* hay VnpayIpnResponse)

PaymentCallback = record trung lập { txnRef, amount, success, providerTxnNo }
IpnResult       = enum trung lập { SUCCESS, INVALID_SIGNATURE, ORDER_NOT_FOUND, ALREADY_PROCESSED, INVALID_AMOUNT }
```

**Ranh giới:** logic nghiệp vụ (idempotency, khớp tiền, đổi status) ở `PaymentService` — chung mọi cổng. Dịch `vnp_*` ↔ trung lập + format ack là riêng VNPay → trong `VnpayService`.

Phần kiến trúc (DTO, enum, rename interface, `PaymentService` neutral, controller) do assistant làm; **2 method gateway-specific** (`parseCallback` + `buildIpnResponse`) để người học code.

### `IpnResult` enum + `PaymentCallback` record
```java
public enum IpnResult { SUCCESS, INVALID_SIGNATURE, ORDER_NOT_FOUND, ALREADY_PROCESSED, INVALID_AMOUNT }
public record PaymentCallback(String txnRef, long amount, boolean success, String providerTxnNo) {}
```

### `PaymentGateway` interface
```java
public interface PaymentGateway {
    String createPaymentUrl(Long orderId, String txnRef, BigDecimal amount, String ipAddr);
    boolean verifySignature(Map<String, String> params);
    PaymentCallback parseCallback(Map<String, String> params);
    Object buildIpnResponse(IpnResult result);
}
```

### Payoff — `PaymentService.handleIpn` sạch bong, KHÔNG còn một chữ `vnp_`
```java
public Object handleIpn(Map<String, String> params) {
    if(!paymentGateway.verifySignature(params)) return paymentGateway.buildIpnResponse(IpnResult.INVALID_SIGNATURE);
    PaymentCallback cb = paymentGateway.parseCallback(params);          // ← dịch sang trung lập
    Optional<Payment> po = paymentRepository.findByTxnRef(cb.txnRef());
    if(po.isEmpty()) return paymentGateway.buildIpnResponse(IpnResult.ORDER_NOT_FOUND);
    Payment payment = po.get();
    if(payment.getStatus() != PENDING) return paymentGateway.buildIpnResponse(IpnResult.ALREADY_PROCESSED);
    long expected = payment.getAmount().multiply(BigDecimal.valueOf(100)).longValue();
    if(cb.amount() != expected) return paymentGateway.buildIpnResponse(IpnResult.INVALID_AMOUNT);
    payment.setRawResponse(params.toString());
    payment.setTransactionNo(cb.providerTxnNo());
    Order order = payment.getOrder();
    if(cb.success()) { payment.SUCCESS; paidAt; order.CONFIRMED; } else payment.FAILED;
    return paymentGateway.buildIpnResponse(IpnResult.SUCCESS);
}
```
→ Thêm MoMo chỉ là viết `MomoService implements PaymentGateway` — `PaymentService` **không đổi một dòng**.

## Review 2 method người học code

### `parseCallback` — ✅ đúng
```java
String tnxRef = params.get("vnp_TxnRef");   // 🟢 tên biến gõ nhầm: tnxRef → txnRef (cosmetic)
long amount = Long.parseLong(params.get("vnp_Amount"));
boolean success = "00".equals(params.get("vnp_ResponseCode"));
String providerTxnNo = params.get("vnp_TransactionNo");
return new PaymentCallback(tnxRef, amount, success, providerTxnNo);
```
Logic dịch `vnp_*` → `PaymentCallback` chuẩn.

### `buildIpnResponse` — chạy đúng nhưng 2 điểm nên sửa

**① Trả `Map.of(...)` → làm `VnpayIpnResponse` thành dead code.** `Map.of("RspCode",...,"Message",...)` serialize JSON đúng y hệt, không sai. Nhưng class `VnpayIpnResponse` (xây riêng, có `@JsonProperty`) giờ không ai dùng → import thừa, class thành rác. Phải chọn 1: dùng lại `VnpayIpnResponse`, hoặc xóa hẳn nó.

**② Statement-switch + biến default có bẫy ẩn.** Khởi tạo `rspCode="00"` rồi switch override 4 case lỗi, SUCCESS rơi default. Nếu sau này thêm `IpnResult` mới (vd `EXPIRED`), nó **âm thầm rơi vào default "00" = báo thành công** — lỗi nguy hiểm compiler không cảnh báo.

→ Dùng **switch EXPRESSION** — gọn + **bắt buộc xử lý đủ mọi enum** (thiếu case là compile error):
```java
@Override
public Object buildIpnResponse(IpnResult result) {
    return switch (result) {
        case SUCCESS           -> new VnpayIpnResponse("00", "Confirm Success");
        case INVALID_SIGNATURE -> new VnpayIpnResponse("97", "Invalid Checksum");
        case ORDER_NOT_FOUND   -> new VnpayIpnResponse("01", "Order not found");
        case ALREADY_PROCESSED -> new VnpayIpnResponse("02", "Order already confirmed");
        case INVALID_AMOUNT    -> new VnpayIpnResponse("04", "Invalid Amount");
    };
}
```
Ba cái lợi: (a) dùng lại `VnpayIpnResponse` → hết dead code, (b) exhaustive check — thêm enum mới compiler ép handle, (c) không cần biến mutable + `default`.
> Ghi chú: interface khai `Object buildIpnResponse(...)` nhưng override được phép **thu hẹp kiểu trả về** (covariant return) thành `VnpayIpnResponse`.

**Người học sửa xong** → build pass + **E2E 6/6 vẫn xanh y hệt** → refactor không đổi hành vi, chỉ đổi cấu trúc. Response vẫn đúng `{"RspCode":"00","Message":"..."}` (chứng minh `VnpayIpnResponse` + `@JsonProperty` vẫn hoạt động qua đường `Object`).

## Tổng kết

**Kết quả:**
- `PaymentGateway` (bỏ tiền tố `I`) + `PaymentCallback` (record trung lập) + `IpnResult` (enum trung lập).
- `VnpayService implements PaymentGateway`: `parseCallback` + `buildIpnResponse` (switch expression exhaustive).
- `PaymentService.handleIpn/handleReturn`: gỡ sạch `vnp_*` + `VnpayIpnResponse` → gateway-agnostic.
- Config `payment-gate.type` + `payment-gate.vnpay.*`; `@ConditionalOnProperty` chọn impl.

**Kiến thức cốt lõi:**
- **Strategy pattern + DIP**: `PaymentService` phụ thuộc abstraction, không phải cổng cụ thể.
- **Leaky abstraction**: trừu tượng nửa vời (chỉ createUrl+verify) vẫn để lộ chi tiết cổng ở tầng callback → phải đẩy `parseCallback` (dịch về DTO trung lập) vào interface mới hết rò rỉ.
- **Ranh giới đúng**: logic nghiệp vụ chung → service; dịch key + ký + ack riêng → gateway impl.
- **1-cổng (`@ConditionalOnProperty`) vs nhiều-cổng (Map runtime)** — chọn theo nhu cầu; multi-gateway cho phép user chọn cổng lúc checkout.
- **MoMo/PayPal**: tư duy giống hệt, cơ chế khác (server-to-server create, chữ ký khác thuật toán/thứ tự, PayPal asymmetric cert).
- **switch expression** exhaustive an toàn hơn statement-switch + default (compiler bắt thiếu case).
- Covariant return: override thu hẹp `Object` → `VnpayIpnResponse` hợp lệ.

**Backlog:** multi-gateway runtime (Map<provider, gateway>) + `getProvider()`; DRY `buildHashData` dùng chung `createPaymentUrl` + `verifySignature`.
