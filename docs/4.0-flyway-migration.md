# Flyway — Database Migration (versioning cho schema DB)

## 1. Vấn đề Flyway giải quyết (ta vừa sống trong nỗi đau này)

Câu hỏi cốt lõi: **làm sao tiến hóa schema DB theo thời gian** — qua nhiều môi trường (dev/staging/prod), qua nhiều người trong team — một cách **an toàn, tái lập được, có lịch sử**?

Từ đầu dự án tới giờ dùng `ddl-auto: update` — và đã thấy nó hỏng thế nào:
- Cột `user_id` mồ côi **chặn mọi lệnh tạo đơn**.
- Bảng `carts_cart_items` rác.
- Hibernate **đoán** phải làm gì, chỉ biết **thêm**, không biết **xóa/sửa** → drift tích tụ.

Hai lựa chọn "cùi" mà mọi team đều từng vướng:

```
① ddl-auto: update          ② Chạy SQL thủ công
   Hibernate tự đoán            Ai đó gõ ALTER TABLE bằng tay trên mỗi môi trường
   → additive-only, drift       → không ai nhớ đã chạy gì, "chạy máy tôi thì được"
   → CẤM dùng ở production       → prod lệch dev, mỗi máy một kiểu
```

→ **Database migration** ra đời: coi schema DB như **code có version control**. Mỗi thay đổi = một file SQL đánh số, chạy đúng một lần, có ghi lại.

## 2. Flyway là gì

Viết các **script SQL đánh version**:
```
V1__create_initial_schema.sql
V2__add_payments_table.sql
V3__drop_orphan_user_id.sql
```
Flyway đọc chúng, **áp dụng theo thứ tự version**, **mỗi cái đúng 1 lần**, và ghi lại đã chạy gì vào bảng `flyway_schema_history`.

> **So với Node.js:** đây chính là **Knex migrations / Sequelize migrations / Prisma Migrate / TypeORM migrations** — cùng khái niệm y hệt. Nếu từng `knex migrate:latest` hay `prisma migrate deploy` thì Flyway là bản Java của nó. Khác biệt: Flyway thiên về **SQL thuần** (viết SQL trực tiếp), còn Prisma/Sequelize hay sinh migration từ model.

## 3. Cơ chế bên trong (deep)

### Bảng `flyway_schema_history` — bộ nhớ của Flyway

Flyway tạo một bảng trong chính DB để **nhớ đã chạy migration nào**:

```
flyway_schema_history
┌─────────┬──────────────────────┬───────────┬─────────────────────┬─────────┐
│ version │ description          │ checksum  │ installed_on        │ success │
├─────────┼──────────────────────┼───────────┼─────────────────────┼─────────┤
│ 1       │ create initial schema│ 892374...  │ 2026-07-25 10:00    │ 1       │
│ 2       │ add payments table   │ 118273...  │ 2026-07-26 09:30    │ 1       │
└─────────┴──────────────────────┴───────────┴─────────────────────┴─────────┘
```

### Luồng chạy khi app khởi động

```
App start → Flyway chạy TRƯỚC khi Hibernate/app sẵn sàng:
  1. Quét thư mục migration → thấy V1, V2, V3
  2. Đọc bảng flyway_schema_history → biết V1, V2 đã chạy
  3. So sánh → V3 là PENDING (chưa chạy)
  4. Áp dụng V3 theo thứ tự → ghi 1 dòng mới vào history
  5. Xong → app tiếp tục khởi động
```

Chạy lại app lần sau: V1, V2, V3 đều đã có trong history → **không chạy lại** → idempotent. (Đúng tinh thần idempotency của IPN vừa học — làm N lần = làm 1 lần.)

### Checksum — kỷ luật bất biến (điểm nhiều người mới vấp)

Flyway **hash nội dung mỗi file migration** và lưu vào `checksum`. Nếu **sửa một migration ĐÃ chạy**:
```
V2__add_payments.sql  đã chạy, checksum lưu = 118273
Sửa nội dung V2        → checksum mới = 998812
App start → Flyway thấy 118273 ≠ 998812 → NÉM LỖI, từ chối khởi động
```
Đây là **tính năng, không phải bug**. Nó ép một kỷ luật vàng:
> **Migration đã chạy là BẤT BIẾN — không bao giờ sửa. Cần đổi gì thì viết migration MỚI (V4, V5...).**

Lý do: sửa V2 sau khi nó chạy ở prod → máy dev mới (chạy V2 bản sửa) có schema **khác** prod (chạy V2 bản cũ) → drift quay lại. Checksum chặn đứng. (Giống Git commit đã push thì không rebase — "lịch sử đã công bố thì bất biến".)

### Quy ước đặt tên
```
V2__add_payments_table.sql
│   │└─ description (dấu _ → space khi hiển thị)
│   └── HAI dấu gạch dưới (bắt buộc)
└────── V = versioned (chạy 1 lần), số version
```
Còn `R__...sql` (repeatable, chạy lại khi đổi — cho view/function) và `U2__` (undo — bản trả phí). E-commerce chỉ cần `V`.

## 4. Bài toán riêng của dự án: baseline DB đã có sẵn

DB đã có schema (ddl-auto tạo) + data test. Không thể "chạy V1 tạo mới". Phải **baseline** — bảo Flyway "coi trạng thái hiện tại là điểm xuất phát V1, đừng cố tạo lại". Đây chính là tình huống gặp ở công ty: áp Flyway vào dự án đang chạy, không phải dự án mới toanh.

## Q&A: ddl-auto nên đặt thành gì khi chuyển Flyway

**Trả lời (người học):** `validate`.

Chuẩn xác. Giải thích:
- **`validate` ✅** — Hibernate **không đụng** schema nữa (Flyway toàn quyền), nhưng vẫn **đối chiếu** entity ↔ schema lúc start. Thiếu cột/lệch kiểu → **báo lỗi ngay lúc khởi động**. Lưới an toàn: thêm field entity mà quên migration → app không start (thay vì 500 lúc runtime như vụ checkout).
- **`none` ❌** — Flyway lo schema nhưng **mất lưới**: quên migration thì app vẫn start, nổ lúc runtime.
- **`update` ❌** — để Hibernate + Flyway **cùng sửa schema** = hai thằng giành nhau → drift + hỗn loạn.

> Cặp đôi chuẩn production: **Flyway đổi schema + Hibernate `validate` canh gác.**

## Người học hỏi: Tích hợp Flyway vào DB đã có sẵn cần những bước gì? Và annotation @OneToMany giữ hay bỏ, thêm sau có phải viết SQL không?

# A. Tích hợp Flyway vào dự án đã có DB — các bước cụ thể

### Bước 1 — Thêm dependency
`flyway-core` + `flyway-mysql` (MySQL 8+ cần module riêng).

### Bước 2 — Chụp ảnh schema hiện tại thành `V1__baseline.sql`
Không tự gõ tay — dump từ DB thật:
```bash
mysqldump --no-data --skip-comments ecommerce > V1__baseline.sql
```
`--no-data` = chỉ cấu trúc. File này = "vạch xuất phát", đặt vào `src/main/resources/db/migration/`.

### Bước 3 — Báo Flyway "DB hiện tại coi như đã ở V1" (baseline)
```yaml
spring.flyway.baseline-on-migrate: true
spring.flyway.baseline-version: 1
```
Lần đầu chạy trên DB cũ (đã có bảng, chưa có `flyway_schema_history`):
```
Flyway thấy: DB non-empty + chưa có bảng history
  → tạo bảng flyway_schema_history
  → chèn 1 dòng "baseline V1" (KHÔNG chạy V1__baseline.sql — schema đã có rồi)
  → từ đó chỉ chạy V2, V3...
```

### Bước 4 — Đổi `ddl-auto: validate`
Flyway sở hữu schema; Hibernate chỉ canh gác.

### Bước 5 — Verify baseline có ĐÚNG không (pro tip)
Dựng một DB rỗng throwaway, cho Flyway chạy V1 từ đầu, rồi so schema kết quả với DB prod. Khớp → `V1__baseline.sql` chính xác. Lệch → sửa V1 (lúc này V1 chưa "công bố" nên sửa được). Đảm bảo máy mới build ra schema y hệt máy cũ.

### Bước 6 — Từ nay mọi thay đổi = migration mới
V2, V3... Không bao giờ sửa cái đã chạy (checksum chặn).

```
DÒNG THỜI GIAN:
  [DB cũ có sẵn] ──baseline──> V1 (đánh dấu, không chạy) ──> V2 ──> V3 ──> ...
  [DB mới rỗng ] ───────────> V1 (CHẠY, dựng full) ──────> V2 ──> V3 ──> ...
                              cùng một bộ file → hai môi trường đồng nhất
```

> Điểm mấu chốt: **schema đang có TRỞ THÀNH V1 (baseline), chỉ viết migration từ V2 trở đi.** `V1__baseline.sql` tồn tại để máy mới dựng lại được từ đầu; trên máy cũ nó bị skip.

# B. Annotation quan hệ (@OneToMany...) — giữ hay bỏ? Có phải viết SQL nữa không?

Flyway và JPA annotation là **HAI việc khác nhau**, không thay thế nhau.

```
@ManyToOne @JoinColumn(name="category_id")     Flyway V5__...sql:
  ↓                                              ↓
"Hibernate ơi, ở RUNTIME hãy map field          "DB ơi, hãy TẠO cột category_id
 category ↔ cột category_id, đây là FK,          + ràng buộc FOREIGN KEY trong bảng"
 biết cách JOIN/nạp quan hệ"
= ORM mapping (Java ↔ bảng, lúc chạy)          = CẤU TRÚC DB thật (DDL)
```

## → GIỮ LẠI toàn bộ annotation quan hệ. Bắt buộc.
Annotation không thừa với Flyway. Flyway không biết gì về object Java — chỉ chạy SQL. Hibernate cần `@OneToMany`/`@ManyToOne`/`@JoinColumn` để nạp và điều hướng quan hệ lúc chạy (`payment.getOrder()`, `cart.getCartItems()`...). Bỏ đi là entity gãy.

## → CÓ, thêm quan hệ mới thì phải viết CẢ SQL migration.
```
TRƯỚC (ddl-auto: update):
  Thêm @ManyToOne @JoinColumn(name="category_id")
  → Hibernate TỰ tạo cột + FK (đoán mò, dễ drift)

SAU (ddl-auto: validate + Flyway):
  Thêm @ManyToOne @JoinColumn(name="category_id")   ← annotation: cách Hibernate map
  + PHẢI viết V5__add_category_to_product.sql:        ← migration: tạo cột thật
      ALTER TABLE products ADD COLUMN category_id BIGINT NOT NULL;
      ALTER TABLE products ADD CONSTRAINT fk_product_category
            FOREIGN KEY (category_id) REFERENCES categories(id);
```
Hai bên **phải khớp**. Annotation ghi `category_id` mà migration tạo `cat_id` → `ddl-auto: validate` **báo lỗi lúc start** (lưới an toàn).

## Tinh tế: chỉ OWNING side mới sinh SQL
```
@ManyToOne @JoinColumn(name="cart_id")   ← OWNING side → CÓ cột cart_id → viết SQL
@OneToMany(mappedBy="cart")              ← INVERSE side → CHỈ điều hướng Java → KHÔNG viết SQL
```
Đúng hệ quả của vụ `carts_cart_items`: `@OneToMany` thiếu `mappedBy` (owning, unidirectional) → Hibernate tạo join table; thêm `mappedBy` → FK dời về `cart_items.cart_id`. Với Flyway, ta kiểm soát tường minh bằng SQL → không còn rác mồ côi.

**Quy tắc vàng khi viết migration:** chỉ viết DDL cho **owning side** (`@JoinColumn`/`@JoinTable`). `mappedBy` là điều hướng Java → không có SQL.

## Bước 2 — sinh V1__baseline.sql (người học tự làm)

### Lệnh đầy đủ
```bash
docker exec -e MYSQL_PWD=admin ecommerce-mysql \
  mysqldump --no-data --no-tablespaces --skip-add-drop-table -uroot ecommerce \
  | sed -E 's/ AUTO_INCREMENT=[0-9]+//' \
  > api/src/main/resources/db/migration/V1__baseline.sql
```

### Mổ xẻ từng mảnh
| Mảnh | Ý nghĩa |
|---|---|
| `docker exec -e MYSQL_PWD=admin ecommerce-mysql` | chạy trong container; `MYSQL_PWD` truyền password qua env → hết cảnh báo "password insecure" |
| `mysqldump` | công cụ export của MySQL |
| `--no-data` | chỉ lấy cấu trúc (CREATE TABLE), bỏ INSERT. Baseline là hình dạng schema |
| `--no-tablespaces` | bỏ mệnh đề tablespace → khỏi cần quyền PROCESS |
| `--skip-add-drop-table` | không chèn `DROP TABLE IF EXISTS` trước mỗi CREATE |
| `-uroot ecommerce` | user root, database ecommerce |
| `\| sed -E 's/ AUTO_INCREMENT=[0-9]+//'` | xóa bộ đếm `AUTO_INCREMENT=123` → DB mới đếm từ 1 |
| `> .../V1__baseline.sql` | ghi vào thư mục Flyway quét mặc định: `resources/db/migration/` |

### Tips cho bước này (kinh nghiệm đi làm)
**① Dump từ "nguồn sự thật", không phải máy dev.** Baseline nên chụp từ schema **production** (hoặc bản sao trung thực), vì DB dev có thể đã tự drift.

**② Luôn `--no-data`.** Baseline chỉ là schema. Seed data là việc riêng.

**③ Cắt "rác đặc thù môi trường" — đặc biệt `DEFINER`.** Nếu có view/trigger/stored procedure, mysqldump chèn `DEFINER=`root`@`localhost`` → gắn cứng user cụ thể → fail ở môi trường khác. Cắt:
```bash
sed -E 's/DEFINER=`[^`]*`@`[^`]*` //g'
```

**④ Giữ phần `SET FOREIGN_KEY_CHECKS=0`.** mysqldump tự bọc `/*!40014 ... FOREIGN_KEY_CHECKS=0 */` → tạo bảng không lo thứ tự FK. **Đừng** dùng `--compact` (cắt mất mấy dòng này → vỡ thứ tự).

**⑤ Verify baseline tái lập CHÍNH XÁC.** Tạo DB rỗng → Flyway chạy V1 → mysqldump → diff với DB gốc → giống hệt = chuẩn. Lệch → sửa V1 ngay (chưa "công bố").

**⑥ Đọc lại file bằng mắt trước khi commit.** Nó chạy trên mọi môi trường mới → phải sạch. Xong rồi thì V1 bất biến vĩnh viễn.

## Bước 3 — application.yaml
```yaml
  jpa:
    hibernate:
      ddl-auto: validate          # Flyway sở hữu schema; Hibernate chỉ đối chiếu entity↔schema
  flyway:
    enabled: true
    baseline-on-migrate: true     # DB đã có sẵn → đánh dấu baseline thay vì chạy lại V1
    baseline-version: 1           # coi schema hiện tại là V1
```

### Verify baseline hoạt động (chạy app lần đầu)
Log Flyway kể đúng câu chuyện:
```
Schema history table `ecommerce`.`flyway_schema_history` does not exist yet
Successfully validated 1 migration
Creating Schema History table ... with baseline
Successfully baselined schema with version: 1
Schema `ecommerce` is up to date. No migration necessary.
```
Bảng history có đúng 1 dòng `<< Flyway Baseline >>` (type BASELINE, checksum NULL — vì không chạy script nào). App start OK = Hibernate `validate` PASS.

## Người học tự làm Bước 5 (verify throwaway DB) + xử lý sự cố môi trường

Ý tưởng: dựng DB **rỗng** riêng, chạy `V1__baseline.sql`, so schema kết quả với DB gốc. Chỉ apply **V1** (không V2), vì DB gốc đang ở trạng thái V1-baseline.

**Sự cố gặp phải (Windows + Git Bash + docker):**
- `docker exec -i ... < file` (redirect phía host) → docker CLI chèn dòng rác `"failed to get console mode for stdout: The handle is invalid."` vào stdin của mysql → SQL lỗi dòng 1.
- `docker cp .../:/tmp/...` → Git Bash **mangle path** (đổi `/tmp` thành `C:/Users/.../Temp`).
- → Đây là lỗi của môi trường tự động headless, **máy thật của người học không bị**.

**Trên terminal thật, các bước:**
```bash
# 1. tạo DB rỗng
docker exec ecommerce-mysql mysql -uroot -padmin -e "CREATE DATABASE ecommerce_verify;"
# 2. apply V1 (Git Bash/CMD)
docker exec -i ecommerce-mysql mysql -uroot -padmin ecommerce_verify < V1__baseline.sql
#    (PowerShell không hỗ trợ <, dùng: Get-Content V1__baseline.sql -Raw | docker exec -i ...)
# 3. đếm bảng → kỳ vọng 11
docker exec ecommerce-mysql mysql -uroot -padmin -N -e "SELECT COUNT(*) FROM information_schema.tables WHERE table_schema='ecommerce_verify';"
# 4. so schema
docker exec ecommerce-mysql mysqldump --no-data --skip-comments --ignore-table=ecommerce.flyway_schema_history -uroot -padmin ecommerce > orig.sql
docker exec ecommerce-mysql mysqldump --no-data --skip-comments -uroot -padmin ecommerce_verify > verify.sql
diff orig.sql verify.sql
# 5. dọn
docker exec ecommerce-mysql mysql -uroot -padmin -e "DROP DATABASE ecommerce_verify;"
```
→ Không khác gì (hoặc chỉ khác `AUTO_INCREMENT=<số>`) = baseline chuẩn.

## Bước 4 — viết migration thật đầu tiên (V2, người học tự viết)

`V2__drop_orphan_join_table.sql`:
```sql
-- V2: Dọn bảng join mồ côi carts_cart_items (drift ddl-auto để lại).
DROP TABLE IF EXISTS carts_cart_items;
```
`IF EXISTS` để an toàn cả 2 tình huống (DB rỗng: V1 tạo → V2 drop; DB cũ: đang có → V2 drop).

> Lưu ý gặp phải: file bị dính ký tự thừa `T` ở dòng 1 (`T-- V2:...`) do gõ nhầm — `T` không nằm trong comment nên Flyway parse thành SQL lỗi. Phải xóa.

## Người học hỏi: apply V2 như nào? (đã viết script trong file)

### Điểm mấu chốt: KHÔNG chạy V2 bằng tay trong DataGrip
Flyway **tự động chạy khi app khởi động**. Chạy tay trong DataGrip → bảng bị drop nhưng Flyway **không biết** (không có dòng V2 trong history) → lần sau start app lại cố chạy V2 → lệch trạng thái.

→ **"Apply V2" = chỉ cần khởi động lại app.** Flyway:
```
1. đọc flyway_schema_history → thấy baseline V1
2. quét file → thấy V2 PENDING
3. chạy V2 → DROP TABLE carts_cart_items
4. ghi 1 dòng version=2 vào flyway_schema_history
Hibernate validate → PASS
```
Verify: `carts_cart_items` biến mất + history có dòng V2 (type SQL, success=1). Start app lần nữa → `No migration necessary` → không chạy lại (idempotent).

## Người học hỏi: Flyway chỉ tạo history khi thực sự đổi database à, nếu không thì không tạo?

Gần đúng, nhưng chỉnh cho chính xác:

### Bản ghi history sinh ra khi Flyway **CHẠY (execute)** một migration, KHÔNG phải khi "database thực sự thay đổi"

Ví dụ sắc bén:
```sql
-- V2: DROP TABLE IF EXISTS carts_cart_items;
```
Giả sử bảng đã không còn (drop tay từ trước). Flyway chạy V2:
- `DROP TABLE IF EXISTS` → không xóa gì → **database KHÔNG đổi**.
- **Nhưng Flyway VẪN ghi 1 dòng V2** ✅ — vì đã **execute** file V2.

→ Flyway không soi "DB có đổi không". History = danh sách **migration đã thực thi**, không phải **các thay đổi thực tế**.

| Tình huống | Ghi history? |
|---|---|
| Flyway **chạy** V2 (dù no-op như DROP IF EXISTS trên bảng không tồn tại) | ✅ CÓ (đã execute) |
| Flyway start nhưng **không có migration PENDING** | ❌ KHÔNG (không chạy gì) |
| Migration đã có trong history → không chạy lại | ❌ KHÔNG (đã ghi từ trước) |
| Migration chạy nhưng **FAILED** | ✅ CÓ, với `success=0` (đánh dấu để sửa) |

> Cách nhớ: **1 dòng history = "đã chạy migration này 1 lần rồi, đừng chạy lại"** — dấu chân của việc *thực thi*, không phải của việc *thay đổi dữ liệu*.

## Người học hỏi: nguyên tắc tạo file migration (tên file, nội dung)?

# A. Nguyên tắc đặt TÊN FILE

## Cấu trúc bắt buộc
```
V2__drop_orphan_join_table.sql
│ │  │                       └─ đuôi .sql
│ │  └───────────────────────── description: các từ nối bằng 1 gạch dưới
│ └──────────────────────────── HAI gạch dưới
└────────────────────────────── prefix V + số version
```

| Thành phần | Luật |
|---|---|
| **Prefix** | `V` = versioned (1 lần), `R` = repeatable (chạy lại khi đổi — view/function), `U` = undo (trả phí) |
| **Version** | tăng dần, **duy nhất** (V1, V2, V2.1...). Hai file cùng version → Flyway lỗi (đúng vụ `V2__baseline` trùng đã gặp) |
| **`__`** | **hai** gạch dưới — thiếu 1 là không nhận |
| **Description** | từ nối bằng **một** gạch dưới; Flyway đổi `_` → space |

## Chiến lược đánh version (quan trọng khi làm team)
```
① Tuần tự:   V1, V2, V3...        ✅ đơn giản  ❌ team đông: 2 người cùng chọn V5 → conflict
② Timestamp: V20260725143000__... ✅ gần như không trùng → hợp team lớn  ❌ dài, khó nhẩm thứ tự
```
> Dự án nhỏ/học: tuần tự. Công ty team đông: nhiều nơi dùng timestamp. Chốt convention với team **ngay từ đầu**.

# B. Nguyên tắc NỘI DUNG

## Ba luật vàng
**① Migration đã chạy là BẤT BIẾN.** Đã apply ở bất kỳ đâu thì không bao giờ sửa (checksum báo lỗi). Cần đổi → viết migration MỚI (fix-forward). Giống commit đã push thì không rebase.

**② Một migration = một thay đổi mạch lạc.** Không nhồi nhiều việc không liên quan vào 1 file.

**③ Forward-only.** Community edition không có undo. Muốn "hoàn tác" V5 → viết V6 làm điều ngược lại.

## Các nguyên tắc thực hành
| Nguyên tắc | Vì sao |
|---|---|
| Phòng thủ `IF EXISTS`/`IF NOT EXISTS` | an toàn khi chạy trên nhiều môi trường trạng thái khác nhau |
| Không để rác đặc thù môi trường | DEFINER, path tuyệt đối, IP hardcode → vỡ ở môi trường khác |
| DDL + DML đều được | không chỉ CREATE/ALTER mà có thể INSERT/UPDATE (seed, backfill) |
| Đọc lại + review như code | migration là code, chạy trên prod |
| Test trên bản sao trước | như bước verify throwaway DB |
| Không sửa schema tay ngoài Flyway | một khi Flyway sở hữu schema, mọi thay đổi qua migration |

## ⚠️ Bẫy riêng MySQL: DDL KHÔNG có transaction
```
Postgres: DDL trong transaction → migration fail giữa chừng → rollback sạch
MySQL:    DDL TỰ auto-commit từng câu → migration 3 câu fail ở câu 2
          → câu 1 ĐÃ commit, không rollback → DB kẹt nửa vời + history success=0
```
Hệ quả với MySQL:
- **Giữ migration NHỎ** → fail thì phạm vi hỏng nhỏ.
- Fail rồi → `flyway repair` (xóa dòng success=0) + **tự tay dọn** phần đã chạy dở, rồi chạy lại.

## Ví dụ nội dung điển hình
```sql
-- V5: thêm quan hệ product → category (owning side @JoinColumn)
ALTER TABLE products ADD COLUMN category_id BIGINT NOT NULL;
ALTER TABLE products ADD CONSTRAINT fk_product_category
    FOREIGN KEY (category_id) REFERENCES categories(id);
```
(Chỉ viết SQL cho **owning side** — `mappedBy` là điều hướng Java, không sinh cột.)

## Bảng "đừng làm"
- ❌ Sửa migration đã apply (checksum lỗi).
- ❌ Xóa file migration đã apply khỏi thư mục ("missing migration").
- ❌ Hai file trùng version.
- ❌ Nhồi nhiều việc không liên quan vào 1 file.
- ❌ Sửa schema tay trên prod ngoài Flyway.

> So Node.js: dùng Knex/Prisma/Sequelize migrations thì mọi luật này y hệt (immutable, forward-only, unique version, review as code). Flyway là bản Java, thiên SQL thuần.
